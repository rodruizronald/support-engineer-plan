## Module 10 — Week 10: DNS — Turning Names Into Addresses

### Weekly Objective

Internalize name resolution as a **hierarchy of caches** that you can inspect at every level: your program, the OS, the recursive resolver, and the authoritative server at the bottom. See, in your own machine's lookups and your own Python, that a name has no single answer. It has the answer *this process* got from *this resolver* at *this moment*, and each part of that sentence can change on its own. Learn the four shapes a DNS failure takes and what each one implicates, so that "it's always DNS" stops being a cliché and becomes a check you can actually run.

### Brief Context

Week 9 ended with an IP address, but nobody types one. Every request starts with a **name**, and that name has to become an address before a single packet leaves the NIC. That job belongs to the **Domain Name System**. DNS is a lookup, but it is not one database. Until the mid-1980s it literally was one file, `HOSTS.TXT`, copied to every machine on the network, and it stopped scaling about as fast as you'd expect. What replaced it is a **distributed hierarchy of zones**. Read `www.github.com.` right to left: the **root** (`.`) knows who runs `com`; the **TLD** servers for `com` know who runs `github.com`; and `github.com`'s **authoritative** servers know the actual records. No level knows the whole answer. Each one only knows whom to ask next. That handoff is called **delegation**, and it's why one company can change its records without asking anyone's permission.

Your machine doesn't walk that tree itself. A small **stub resolver** in the OS hands the question to a **recursive resolver**: your home router, your ISP's, a corporate one, or a public one like `8.8.8.8` or `1.1.1.1`. The recursive resolver does the walking and **caches everything it learns**. Caching is the whole design, not an optimization added later. Every answer carries a **TTL** (time to live, in seconds), and every layer between you and the authoritative server is allowed to remember the answer for that long: some application runtimes, the browser, the OS (`mDNSResponder` on macOS, the DNS Client service on Windows), the router, and the recursive resolver. Measured on a real laptop: a name nobody has asked about takes **~300 ms** (full recursion, several round trips); a popular name your resolver already holds takes **~35 ms** (one round trip to the resolver); and the same name a second time takes **~1 ms** (the OS's own cache). That is Week 1's latency hierarchy again, at a new scale. It is also why "DNS propagation" isn't a real process. When someone changes a record, nothing travels anywhere. The old answer just keeps being served from caches you don't control until their TTLs run out. **Negative** answers ("that name doesn't exist") are cached too, which is why a name you created a minute ago can keep failing for a while.

A name holds more than one kind of record. **A** and **AAAA** hold IPv4 and IPv6 addresses. **CNAME** says "this name is an alias; go look up that one instead." It's everywhere in front of CDNs and SaaS products, so the name you asked about is very often not the name that answered: `www.microsoft.com` is two aliases deep before you reach an address owned by Akamai. **MX** says where a domain's mail goes, **TXT** holds free-form proofs (SPF, domain verification tokens), **NS** and **SOA** describe the zone itself, and **PTR** maps an address back to a name. Every one of them shows up in tickets, and the CNAME chain shows up most, because it quietly moves the problem to a different company's DNS.

DNS also fails in distinct ways, and each one points somewhere different. **NXDOMAIN**: the name doesn't exist (a typo, or a record nobody created). **NOERROR with no answer** (often called NODATA): the name exists but has no record of the type you asked for (`github.com` has no AAAA, so no IPv6). **SERVFAIL**: the resolver tried and couldn't produce an answer it trusts (a broken authoritative server, or a DNSSEC signature that doesn't verify). **No response at all**: nobody answered, so the resolver is unreachable or a firewall is eating port 53. How fast it fails is evidence too. A wrong name fails in milliseconds; an unreachable resolver fails only when your timeout runs out. Python flattens most of this into a single `socket.gaierror`, which is the main reason this week teaches you to ask DNS directly.

Finally, resolution is **configured**, and the configuration differs per machine, per network, and per process. The **hosts file** is consulted before DNS. That makes it a favorite debugging trick and a classic cause of "works on my machine," and you'll find lines in it that other software added without asking. The resolver list and the **search domains** come from network settings (`resolv.conf` on Linux, the network configuration on macOS and Windows). A VPN can swap in a resolver that knows **internal-only** names, or gives a different answer for the same name (**split-horizon**). A container gets its own `resolv.conf`, and a browser may skip the OS and use DNS-over-HTTPS. That's why `dig` and your application can disagree at the same moment, and why the most useful question a support engineer can ask about any DNS claim is: **resolved by what, from where, and when?**

### Research Questions

Answer each in your own words in `solutions/answers.md`. Don't copy-paste definitions; explain them as if to a friend.

#### Part A — How a name becomes an address

1. Why does DNS exist, and why is it a distributed hierarchy instead of one big file, which is what it used to be (`HOSTS.TXT`)? Read `www.github.com.` right to left and name the root, the TLD, and the domain. What is a **zone**, what does **delegation** mean, and what makes a server **authoritative** for a name?
2. Walk the **resolver chain**: stub resolver → recursive resolver → root → TLD → authoritative. Who does the walking? What's the difference between a **recursive** and an **iterative** query, and at which steps can a **cache** answer instead? Why does almost no lookup ever actually reach a root server, and why does DNS normally travel over **UDP** (with TCP as a fallback)?
3. Record types: **A, AAAA, CNAME, MX, TXT, NS, SOA, PTR**. Say what each is for, and give one support ticket where each one is the answer. What does a **CNAME chain** do to debugging (the name you asked for vs the name that answered)? Why are CNAMEs so common in front of CDNs and SaaS products, and why can't one sit at a domain's apex (`example.com` itself)? What does a **PTR** record (reverse DNS) prove, and what doesn't it?
4. What is a **TTL**, who sets it, and which layers cache an answer for that long? Name all of them between your Python process and the authoritative server. Why is "DNS propagation" really TTL expiry in caches you don't control? Why does the TTL you see **count down** between two queries? How should a team plan a DNS change (what do they do a day *before*)? And why might a long-running process never pick up a new address at all?
5. Failure shapes. Distinguish **NXDOMAIN**, **NOERROR with no answer** (NODATA), **SERVFAIL**, **REFUSED**, and **no response at all** (timeout), and say which component each one implicates. What is **negative caching**, where does its duration come from (look at the **SOA** record), and why does a name you just created keep failing for a while? Finally, "the name is wrong" vs "the resolver is unreachable": how do those two look different from Python (`socket.gaierror`'s *"not known"* vs *"temporary failure"*), and in how long they take to fail?

#### Part B — Where resolution is configured, and how it disagrees with itself

6. The **hosts file**: where does it live on macOS/Linux and on Windows, why is it consulted *before* DNS, and why is it both a favorite debugging trick and a classic cause of "works on my machine"? Is `localhost` a DNS name? Name one kind of software that edits your hosts file without asking.
7. `resolv.conf` and its equivalents: what do `nameserver`, `search`, `ndots`, and `timeout` do? Use **search domains** to explain why `db` resolves on one machine and not on another, and what `ndots:5` (Kubernetes' default) does to a lookup for `api.github.com`. Why is `/etc/resolv.conf` on macOS mostly a decoy (read its first lines, then run `scutil --dns`), and where does Windows keep the same settings?
8. **Split-horizon DNS** and internal-only names: why does the same name resolve to a private address on the VPN and to a public address (or nothing) off it? Then **DNS inside containers**: where does a container's `/etc/resolv.conf` come from, what is Docker's embedded resolver at `127.0.0.11`, and why is "it works on my laptop but not in the container" so often a DNS story?
9. Why can `dig` (or `nslookup`) and your application get **different answers** for the same name at the same moment? Contrast asking a DNS server directly with calling `getaddrinfo()`, which runs the OS's whole policy: the hosts file, the OS cache, search domains, mDNS for `.local` names, and only asking for AAAA when the machine has IPv6 to use. Then add the browser, which may keep its own cache and use DNS-over-HTTPS. When a customer says "DNS is fine, I checked," what exactly did they check?
10. *(Tie-back to Weeks 1, 5, 6, and 9.)* Trace `socket.getaddrinfo("www.github.com", 443)` from your Python process to the authoritative server and back. Name which config files the OS reads on your behalf (Week 6), which **process** actually performs the lookup (Week 5; it's not yours on macOS or Windows), the **UDP packet** to port 53 and the **ephemeral port** it leaves from (Week 9), each cache that could answer instead, the CNAME, and the list of tuples that comes back. Put a rough cost on each tier against Week 1's latency table (OS cache vs resolver cache vs full recursion), then name one realistic way each step fails.

### Practical Tasks

Each task is a separate, tiny artifact: think 5–20 lines of Python, or, for Task 3, a saved command transcript. Run each one, look at the output, and write one sentence in your notes about what it showed you. Each task practices something from the questions above. Tasks 1, 4, 5, and 6 use `dnspython` (`pip install dnspython`); Task 2 needs only the standard library. **Task 6 is optional**: a stretch for when you want to go further.

1. **Task 1 — Where this machine looks, and what your program actually gets.** *(Practices Q6, Q7, and Q9.)* Two parts. **(a)** Print the active (non-comment) lines of your hosts file: `/etc/hosts`, or `C:\Windows\System32\drivers\etc\hosts` on Windows; pick with `sys.platform`. Then print the system's resolver list and search domains via `dns.resolver.Resolver().nameservers` and `.search`; dnspython reads the right place on each OS, so you don't have to. **(b)** For `localhost`, `example.com`, and any extra name your hosts file lists, print what `socket.getaddrinfo(name, 443)` returns (the unique addresses: what your *application* gets) next to what `8.8.8.8` says for A and AAAA (a resolver built with `Resolver(configure=False)` and `nameservers = ["8.8.8.8"]`; catch `NXDOMAIN` and `NoAnswer`). Look for three disagreements, each one a lesson. **`localhost`**: your program gets `127.0.0.1` and `::1`, and public DNS says **NXDOMAIN**; the answer never left your machine. **A hosts-file line some other tool added** (Docker Desktop adds `kubernetes.docker.internal`): it resolves for you and for nobody else. **`example.com`**: public DNS has AAAA records, but if your machine has no global IPv6 address, `getaddrinfo()` may hand back IPv4 only. The OS doesn't ask for what it can't use (on macOS, `scutil --dns` says *"Request A records"*). **On Windows** the hosts file is usually all comments, because Windows answers `localhost` internally: same answer, different mechanism. **Concepts:** hosts file, `socket.getaddrinfo()`, `dns.resolver.Resolver()`, `configure=False`, `NXDOMAIN` / `NoAnswer`, `sys.platform`.
2. **Task 2 — Time the cache hierarchy.** *(Practices Q2, Q4, and Q5.)* With `time.perf_counter()` around `socket.getaddrinfo()`, time three things, five lookups each. **(1)** A name *nobody* has ever asked for, so every cache misses. A wildcard domain makes one for you: `f"w10-{uuid.uuid4().hex[:8]}.127-0-0-1.sslip.io"` resolves to `127.0.0.1` for any label you invent. **(2)** A popular name you haven't looked up in this session (pick one you don't normally visit). **(3)** A random name that doesn't exist, such as `f"{uuid.uuid4().hex[:8]}.python.org"`. On a real run, (1) cost **~300 ms** the first time (full recursion) and **~1 ms** after (the OS cache). (2) cost **~35 ms** the first time, which is exactly one round trip to a resolver that already had it, then ~1 ms. (3) failed in ~110 ms the first time and ~1 ms after, because the *failure* was cached too: **negative caching**. Print each in milliseconds and set the three tiers next to Week 1's table. Note that Python itself caches nothing. Even the ~1 ms hit is a request to another process (`mDNSResponder` on macOS, the DNS Client service on Windows), which is why it costs a millisecond and not a microsecond. **On Windows,** run `ipconfig /displaydns` (or `Get-DnsClientCache`) right after and find your sslip.io name in the OS cache, with its TTL counting down. **Concepts:** `time.perf_counter()`, `uuid.uuid4()`, cold vs warm lookup, OS cache vs resolver cache vs full recursion, negative caching.
3. **Task 3 — Read the records, then walk the tree yourself.** *(Practices Q1, Q2, and Q3. A shell task: save it as `solutions/task3_read_the_records.md`.)* Run four commands and paste each one's real output with a couple of sentences on what it proved. **(1)** `dig +noall +answer github.com A github.com AAAA github.com MX github.com NS github.com SOA`: notice there's **no AAAA line at all** (GitHub has no IPv6), that the MX points at Microsoft's mail service (MX tells you who runs a company's email), and that the NS list spans **two different DNS providers**. **(2)** `dig +noall +answer www.microsoft.com`: a two-hop **CNAME chain** ending at an Akamai name, with TTLs that *shrink* along the chain (hours on the first alias, seconds on the final address), because the CDN wants to steer you quickly. **(3)** `dig +short -x 8.8.8.8`: reverse DNS, which says `dns.google.` **(4)** `dig +trace +nodnssec @1.1.1.1 example.com`: the whole walk, root → `com` → the domain's own servers → the answer. Compare the TTL at the bottom (the full value, straight from the source) with what `dig +noall +answer example.com` shows through your normal resolver: usually smaller, because there it's counting down in a cache. Also note how long the `com` delegation is cached: 172800 seconds, two days. The `@1.1.1.1` matters: some ISP resolvers won't answer the non-recursive root query `+trace` starts with, and you get one line (*"Received 28 bytes from …"*) and nothing else. That happened on the machine these tasks were verified on. **On Windows** there's no `dig`; use `Resolve-DnsName` (`-Type MX`, `-Type NS`, `-Type SOA`; `Resolve-DnsName www.microsoft.com` shows the chain; `Resolve-DnsName 8.8.8.8` does the PTR). For (4), do the walk **by hand**, which is worth doing once anyway: `Resolve-DnsName example.com -Server a.root-servers.net -NoRecursion`, then repeat against one of the `com` servers it names, then against one of the domain's own servers. **Concepts:** `dig`, record types, CNAME chain, PTR, `+trace`, delegation, referral, authoritative TTL vs cached TTL.
4. **Task 4 — Three resolvers, three clocks.** *(Practices Q4 and Q9.)* Build three dnspython resolvers: the system one (`Resolver()`), `8.8.8.8`, and `1.1.1.1`. For `github.com` and `www.microsoft.com`, resolve A from each and print the sorted addresses, `answer.rrset.ttl`, `answer.canonical_name`, and the milliseconds it took. `time.sleep(5)`, then do it all again. Things to look for, all seen on a real run: the TTL from one resolver **drops by about 5** between rounds, because it's the time *remaining in that cache*, not the record's setting. `8.8.8.8` may *not* count down cleanly, because it isn't one cache; it's a fleet of caches behind one anycast address. The resolvers give **different addresses** for `www.microsoft.com`, because a CDN answers based on where the resolver is, so disagreement is not automatically a fault. `canonical_name` shows the end of the CNAME chain without you following it. And one sample may take **~2 seconds**: that's a UDP packet that got lost and dnspython's retry, which is Week 9's best-effort delivery showing up in your own timings. **Concepts:** `dns.resolver.Resolver`, `nameservers`, `rrset.ttl`, `canonical_name`, cache countdown, anycast, geo-steered answers.
5. **Task 5 — Make DNS fail four ways.** *(Practices Q5 and Q9.)* Using a dnspython resolver pointed at `8.8.8.8` with `lifetime = 2`, provoke each failure shape and print the exception class name and how many milliseconds it took to fail. **NXDOMAIN**: `does-not-exist.python.org`. **NODATA**: `github.com`, type `AAAA` → `NoAnswer`. **SERVFAIL**: `dnssec-failed.org`, a domain whose DNSSEC signatures are broken *on purpose*, so a validating resolver refuses to answer → `NoNameservers`. **Timeout**: `example.com` against a resolver at `192.0.2.1`, a documentation-only address where nothing answers → `LifetimeTimeout`. Then pass the first three names through `socket.getaddrinfo()` and print the `gaierror`'s `errno` and message. Notice how much the OS throws away: on macOS, NXDOMAIN and NODATA both come back as the same `errno 8`. And `dnssec-failed.org` may **succeed** through your system resolver: the ISP resolver on the verifying machine doesn't check DNSSEC, so it handed back an address that `8.8.8.8` and `1.1.1.1` both refused. Two resolvers, two verdicts, one name. Two more things to notice: the failures that come back in tens of milliseconds are *answers*, while the timeout costs your full `lifetime` (fast failure and slow failure point at different problems). And as a bonus, try `does-not-exist.example.com`: you'd expect NXDOMAIN and get `NoAnswer` instead, because `example.com` is hosted on Cloudflare, which answers every nonexistent name with "exists, no records." Textbook categories meet real providers. **Concepts:** `NXDOMAIN`, `NoAnswer`, `NoNameservers` (SERVFAIL), `LifetimeTimeout`, `lifetime=`, `socket.gaierror.errno`, DNSSEC validation.
6. **Task 6 — A DNS query by hand.** *(Optional; practices Q2 and Q5, plus Weeks 2 and 9.)* Build a query with no DNS library: a 12-byte header packed with `struct.pack("!HHHHHH", query_id, 0x0100, 1, 0, 0, 0)` (a random ID, the "recursion desired" flag, one question), then the name as **length-prefixed labels** (`\x07example\x03com\x00`), then type A and class IN (`struct.pack("!HH", 1, 1)`). That's 29 bytes for `example.com`. Send it with a `SOCK_DGRAM` socket to `("8.8.8.8", 53)` with a 2-second timeout, `recvfrom()` the reply, and unpack its first 12 bytes the same way: check the ID matches, read the answer count, and read the **RCODE** from the low 4 bits of the flags. Print the reply as a hex dump (Week 2's habit) and find, by eye, your name echoed back as `07 65 78 61 6d 70 6c 65 03 63 6f 6d 00`, a `c0 0c` (a pointer back to byte 12, so the name isn't repeated), the 4-byte TTL, and the 4 bytes of each address. Then ask for `does-not-exist.python.org`: the flags change from `81 80` to `81 83`. NXDOMAIN is one nibble, `3`. Every "DNS error" you will ever see in a ticket started as that nibble. **Concepts:** `struct.pack` / `unpack`, network byte order (`!`), DNS header, QNAME labels, RCODE, UDP port 53, name compression.
