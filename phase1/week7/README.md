## Module 7 — Weeks 7–8: Processes, the Shell, and Program Launch

### Weekly Objective

Internalize what actually happens between pressing Enter and a program running — the shell parsing and *rewriting* your command line, finding the program on `PATH`, forking and exec'ing a new process, and wiring up its three standard streams — and see, in your own running Python code, the things that make this layer fail in production: "command not found" in cron, a filename with a space that breaks a script, `shell=True` executing an attacker's command, a deploy that ploughs on past a failed step, and logs that go silent the moment output is piped.

> **This module covers two weeks.** There's roughly twice the material of a normal week here, so pace it: **Part A** (the shell and how a program gets launched) in the first week, **Part B** (doing it from Python) in the second, then the graduation project. It's also the last module of Phase 1 — the research questions and the project deliberately reach back through all six weeks.

### Brief Context

Week 5 introduced the **process** — an identity the OS hands your running program. This module is about the step just before that: *how a process comes into existence in the first place*, and who does the work. The answer is mostly **the shell**, and the shell is far more active than it looks.

A shell — `bash`, `zsh`, `cmd`, PowerShell — is not part of the operating system. It's just a program whose job is to read a line of text, **rewrite** it, and launch other programs. That rewriting step is the part everyone underestimates. Before your program is even loaded, the shell has split your line into words on whitespace, expanded `*.txt` into an actual list of matching filenames, substituted `$HOME` and `$PATH`, stripped your quotes, and decided which parts are the command and which are its arguments. Your program never sees what you typed — it sees the *result*. That single fact explains why a file named `my report.pdf` breaks a naive script (the shell split it into two arguments), why `rm *` is so dangerous (the shell, not `rm`, produced the file list), and why passing untrusted text to `shell=True` is a **command injection** vulnerability rather than a style preference.

Then the shell has to *find* the program. `python` is not a location — it's a name the shell resolves by walking the directories in `PATH` in order and taking the first match. This is why the same command works in your terminal and dies with "command not found" under `cron` or in a container: those run with a different, much smaller `PATH`. It's also why you must type `./script.py` for a file in the current directory — `.` normally isn't on `PATH` at all, and for good security reasons. With the program located, the OS creates the process the classic way: **fork** to duplicate the current process, then **exec** to replace its program image with the new one, leaving a parent/child pair. The parent is then obliged to **wait** for the child and collect its exit code — and a child whose exit status nobody collects becomes a **zombie**.

Finally the shell wires up plumbing. Every process starts life with three open file descriptors (Week 5's small integers): **stdin** (0), **stdout** (1), and **stderr** (2). Redirection (`>`, `2>`, `<`) points those descriptors at files instead of your terminal, and a **pipe** (`|`) connects one process's stdout directly to the next one's stdin — which is why keeping errors on stderr matters, and why `cmd > out.log` still prints errors to your screen. The exit codes coming back are what the shell uses for logic: `&&`, `||`, and the reason a deploy script without `set -e` cheerfully continues after a failure and reports success.

This is where all of Phase 1 converges, and it's where a support engineer spends real time. "The cron job says command not found." "It works in my terminal but not in the container." "The deploy reported success but nothing deployed." "Our container logs are empty until it crashes." "We got shell-injected through a filename." Every one of those is this layer. You'll finish Phase 1 able to trace a single command line all the way down — through the shell, the kernel, the file descriptors, the disk, the bytes, and the objects in RAM — and back up through the exit code.

### Research Questions

Answer each in your own words in `solutions/answers.md`. Don't copy-paste definitions — explain them as if to a friend.

#### Part A — The shell and how a program gets launched

1. What *is* a shell? Explain that it's just a program that reads a line, rewrites it, and launches other programs — then walk the sequence from pressing Enter to a running process (parse → expand → resolve on `PATH` → fork → exec → wait). What's the difference between a shell **builtin** like `cd` and an external command like `ls`, and why can't `cd` be an external program?
2. **Finding the program.** What is `$PATH`, and how does the shell turn the name `python` into an actual file on disk? How do `which` / `command -v` report that, why does "command not found" almost always mean a `PATH` problem rather than a missing program, and why must you write `./script.py` instead of `script.py` for a file in the current directory? (Tie this to Week 6's absolute vs relative paths.)
3. **How a process is really created.** Explain the **fork/exec** model: what `fork` duplicates and what `exec` replaces. Using Week 5's PID/PPID, describe the parent/child relationship, what it means for a parent to **wait for** (reap) a child and collect its exit code, and what a **zombie** and an **orphan** process each are.
4. **Who expands what — the most important idea this week.** Before your program runs, the shell rewrites your command line: **word splitting** on whitespace, **globbing** (`*.txt`), **variable expansion** (`$HOME`), and **quoting** (`'single'` vs `"double"`). Explain why `python script.py *.txt` means the *shell* — not your program — produced that list of filenames, and why a file named `my report.pdf` breaks a script that isn't careful. Then explain why all of this makes passing untrusted text to a shell a **command injection** vulnerability, and what the attacker actually gets to do.
5. **The three standard streams.** What are **stdin**, **stdout**, and **stderr**, and what are their file descriptor numbers (tie back to Week 5)? Explain redirection (`>`, `>>`, `2>`, `2>&1`, `<`) and what a **pipe** (`|`) physically connects to what. Why should a well-behaved program put results on stdout and errors on stderr — and why does `cmd > out.log` still show errors on your screen?

#### Part B — Doing it from Python

6. **Receiving arguments.** What is `sys.argv`, and what's in `sys.argv[0]`? Given Q4, describe what the shell has already done to your command line before your program sees it — so what does `sys.argv` actually contain when you run `myscript.py *.txt "two words"`? Why is `argparse` a better habit than indexing `sys.argv` by hand?
7. **Launching children safely.** Compare `subprocess.run(["ls", "-l"])` with `subprocess.run("ls -l", shell=True)`: what's different about who parses that command, and which is safe with untrusted input (tie to Q4)? Explain `capture_output=True`, `text=True`, `check=True`, and `timeout=`, plus what you get back in `.returncode`, `.stdout`, and `.stderr`. When is `shell=True` a legitimate choice?
8. **Exit codes as control flow.** Week 5 covered what an exit code *is*; this is how it gets *used*. Explain how the shell chains commands with `&&` and `||`, and why a deploy script without `set -e` can continue past a failed step and still report success. Then: how do you make your *own* Python tool a good citizen — meaningful exit codes via `sys.exit()`, errors on stderr, and `check=True` when it calls children?
9. **The environment, and a buffering trap.** How does a child process get its **environment**, and how do you give a child a different one (`env=` in `subprocess`) without changing your own? Then the classic gotcha: why does a Python program's output appear instantly in a terminal but arrive late — or vanish entirely on a crash — when piped or redirected? Explain **line-buffered vs block-buffered** stdout (tie to Week 6's buffering), and the three usual fixes: `print(..., flush=True)`, `python -u`, and `PYTHONUNBUFFERED=1`.
10. *(Capstone — ties together all of Phase 1.)* You type `python analyze.py data.csv | grep ERROR > out.txt` and press Enter. Trace it all the way down and back up, naming every layer: what the **shell** parses and expands, how `python` is **resolved on PATH**, the **fork/exec** that creates the processes, how the **pipe and redirection** are just file descriptors (Week 5), the **file read** of `data.csv` (Week 6), the **bytes** and their **decoding** (Week 2), the **objects** now in RAM with names bound to them (Week 3), the **four components** and their wildly different speeds doing the work (Week 1), and finally the **exit codes** that travel back to the shell. Then name one realistic way each layer can fail.

### Practical Tasks

Each task is a separate, tiny Python file (think 5–20 lines). Run each one, look at the output, and write one sentence in your notes about what it showed you. Each task practices something from the questions above. **Task 6 is optional** — a stretch for when you want to go further.

1. **Task 1 — See what the shell handed you.** *(Practices Q4 and Q6.)* Print `len(sys.argv)` and then each element of `sys.argv` on its own numbered line. Now run it several ways and compare: `python task1_read_argv.py a b c`, then with a quoted argument containing a space (`"two words"`), then with a glob (`*.py`). Watch the glob arrive as *many* arguments and the quoted string arrive as *one* — proof that the shell rewrote your line before Python ever saw it. **Concepts:** `sys.argv`, `sys.argv[0]`, shell word splitting, globbing, quoting.
2. **Task 2 — Find a program the way the shell does.** *(Practices Q2.)* Split `os.environ["PATH"]` on `os.pathsep` and print each directory on its own line — the exact list the shell searches, in order. Then use `shutil.which()` to resolve a few command names (`"python3"`, `"git"`, `"definitely-not-a-real-command"`) and print where each one was found or that it wasn't. You've just reimplemented `which`. **Concepts:** `os.environ`, `os.pathsep`, `shutil.which()`, PATH resolution.
3. **Task 3 — Run a child and capture what it says.** *(Practices Q7.)* Use `subprocess.run([...], capture_output=True, text=True)` to run a command that succeeds, and print `.returncode`, `.stdout`, and `.stderr` separately so you can see the two streams stay apart. Then run a command that *fails*, print its non-zero `.returncode`, and finally run it again with `check=True` inside a `try`/`except subprocess.CalledProcessError` to see Python turn a bad exit code into an exception. **Concepts:** `subprocess.run`, `capture_output=True`, `text=True`, `check=True`, `CalledProcessError`.
4. **Task 4 — Watch a command injection happen (safely, on your own machine).** *(Practices Q4 and Q7.)* Put a hostile-looking string in a variable — `untrusted = "hello; touch INJECTED.txt"` — then pass it to a child process **two ways**: as one element of a list (`[sys.executable, "-c", "import sys; print('arg =', repr(sys.argv[1]))", untrusted]`) and glued into a single string with `shell=True`. Each time, print the argument the child actually received *and* check whether `INJECTED.txt` now exists. With the list form the child reports the **whole string as one literal argument** and no file appears. With `shell=True` the child reports only `'hello'` and **the file gets created** — the shell saw the `;`, cut your command in half, and ran the rest as a second command. Delete the marker file when you're done. **Judge this by the file, not by the printed text:** the word "INJECTED" appears in *both* runs, because it's part of the string being echoed — so the only unambiguous proof is the side effect on disk plus the truncated argument. **On Windows,** `shell=True` runs `cmd.exe`, where `;` is *not* a command separator — use `&` in place of `;` (and `type nul > INJECTED.txt` in place of `touch`) to see the same thing. That difference is itself worth noticing: "which shell am I actually handing this to?" is the question behind a lot of cross-platform breakage. **Concepts:** `subprocess.run` list vs string, `shell=True`, command injection, why quoting is the shell's job.
5. **Task 5 — Build a pipe, and split the streams.** *(Practices Q5.)* Two parts. **(a)** Recreate `cmd1 | cmd2` in Python: start a first child with `subprocess.Popen([...], stdout=subprocess.PIPE)`, pass its `.stdout` as the second child's `stdin=`, and read the final result — you've wired one process's output straight into another's input. Use short `python -c` commands on both ends so it works the same on every OS. **(b)** Write one line to `sys.stdout` and one to `sys.stderr` from the same script, then run it redirecting only stdout (`python task5_pipe_and_streams.py > out.txt`) and watch the error line stay on your screen while the normal line lands in the file. **Concepts:** `subprocess.Popen`, `stdout=subprocess.PIPE`, `stdin=`, `sys.stderr`, shell redirection.
6. **Task 6 — Watch buffering swallow your logs.** *(Optional — practices Q9.)* Print five lines in a loop with a `time.sleep(1)` between them. Run it straight in the terminal: lines appear one per second. Now pipe it (`python task6_buffering.py | cat`) and watch them sit invisible and then arrive **all at once at the end** — because stdout switched from line-buffered to block-buffered the moment it stopped being a terminal. Then fix it three ways and confirm each works: `print(..., flush=True)`, running as `python -u`, and setting `PYTHONUNBUFFERED=1`. This is exactly why a container's logs look empty right up until it dies. **Concepts:** stdout buffering, `flush=True`, `python -u`, `PYTHONUNBUFFERED`, `sys.stdout.isatty()`.
