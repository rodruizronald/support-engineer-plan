## Module 6 — Week 6: Files, Paths, and I/O

### Weekly Objective

Internalize that a **file is just a named sequence of bytes** and a **path is just a string the OS has to resolve** — and see, in your own running Python code, the things that make file I/O go wrong in production: text mode quietly encoding and decoding for you, a `.read()` that pulls a 4 GB file into RAM, a script that can't find its own config because it was launched from a different directory, buffered writes that vanish when a process is killed, and a half-written file that a reader picks up mid-flight.

### Brief Context

A file is a much smaller idea than it looks. It is a **named sequence of bytes** plus some **metadata** — a size, timestamps, an owner, permission bits. That's it. Everything else you associate with files is a layer on top: the **filesystem** is what turns the raw blocks of the disk from Week 1 into a tree of names you can navigate, and a **directory** is itself just a special file whose contents are a list of names pointing at other files. The bytes inside carry no meaning of their own (Week 2) — a `.csv`, a `.jpg`, and a `.log` are all the same kind of thing to the disk, and the extension is a hint for humans, not a fact the OS enforces.

The second idea is that a **path is not a file** — it's a string that has to be *resolved* to one, and that resolution depends on state you might not be thinking about. An **absolute** path (`/var/log/app.log`) says exactly where to look. A **relative** path (`config.yaml`, `../data/`) is resolved against the process's **current working directory** — which is set by whoever *launched* the process, not by where the script file happens to live. That single detail is the entire explanation for "it works when I run it from my editor but not from cron," and it's why `Path(__file__).parent` is one of the most useful three tokens in Python.

The third idea is that writes are **not** what they appear to be. Because the disk is thousands of times slower than RAM (Week 1), nobody writes a byte at a time — your data sits in a **buffer** in your process, then in the OS **page cache**, and only later actually lands on the platter or flash. So `write()` returning successfully does *not* mean the data is safe. If the process is `SIGKILL`ed (Week 5), whatever was still buffered is simply gone, and a reader who opens the file at the wrong moment sees a **truncated, half-written** file. The fix — write to a temporary file, then atomically **rename** it into place — is a pattern you'll see in every serious piece of software once you know to look for it.

None of this is academic. "The disk is full and the service is throwing errors." "We deleted the huge log but `df` still says 100% — because a process still has it open" (Week 5's file descriptors). "The script OOM-killed itself reading one big export." "The CSV imports fine for me and is garbled for the customer" (Week 2's encodings, now arriving through `open()`). "Permission denied in the container, fine on my laptop." This week you learn to see all of it: first what files, paths, metadata, and buffering actually are, then how Python's `open()`, `pathlib`, and error types expose them. It's the layer where the whole phase meets — a path resolved by the OS (Week 5) reaches bytes on disk (Weeks 1–2) that become objects in RAM (Week 3).

### Research Questions

Answer each in your own words in `solutions/answers.md`. Don't copy-paste definitions — explain them as if to a friend.

#### Part A — Files, paths, and the filesystem

1. What *is* a file, underneath? Explain it as "a named sequence of bytes plus metadata," and say what the **filesystem** adds on top of the raw disk from Week 1. What is a **directory**, really — and why is a file's **extension** (`.csv`, `.jpg`) a hint rather than a fact?
2. What's the difference between an **absolute** and a **relative** path, and what is a process's **current working directory**? Explain why a script that opens `config.yaml` can work when you run it from your editor and fail when `cron` or a container runs it — and what `.`, `..`, `~`, and the `/` vs `\` separator each mean.
3. A file's **metadata** is separate from its **contents**. What does the OS track about each file (size, modification time, owner, permission bits) — the things `ls -l` shows you? Explain **read/write/execute** for user/group/other, what "**Permission denied**" is actually telling you, and why *renaming* a huge file is instant while *copying* it is slow.
4. Writes don't hit the disk when you think they do. Explain **buffering** and the OS **page cache**, and why they exist (tie it back to Week 1's latency hierarchy). What's the difference between `flush()` and `fsync()`, what happens to buffered data when a process is `SIGKILL`ed (Week 5), and why can a reader catch a file **half-written**?
5. What happens to a running service when the **disk fills up** (`ENOSPC`)? Explain why deleting a big log file sometimes *doesn't* free the space until you restart the process (tie this back to Week 5's file descriptors), and what **log rotation** is for.

#### Part B — How Python does file I/O

6. In Python's `open()`, what's the difference between **text mode** (`"r"`, `"w"`) and **binary mode** (`"rb"`, `"wb"`)? Walk through the mode characters (`r`, `w`, `a`, `x`, `+`, `b`) — and say precisely what `w` does to an existing file. Which mode gives you `str` and which gives you `bytes`, what does text mode silently do for you (tie back to Week 2's encodings, and the `encoding=` argument), and when *must* you use binary?
7. Reading a 4 GB file with `.read()` can take down a service that reads it line-by-line just fine. Explain the difference between `f.read()`, iterating `for line in f:`, and `f.read(chunk_size)` in terms of **memory footprint** — and using Weeks 1 and 3, explain why "**streaming**" is the default habit you want.
8. Why prefer **`pathlib`** over gluing strings together with `+` or `"/"`? Show what `Path` gives you (`/` to join, `.name`, `.suffix`, `.parent`, `.exists()`, `.stat()`, `.resolve()`), and explain exactly why `Path(__file__).parent / "data.txt"` fixes the "my script can't find its own data file" bug from Q2.
9. What are the common I/O exceptions — `FileNotFoundError`, `PermissionError`, `IsADirectoryError` — and what does each one tell you about *where* to look? Compare checking `path.exists()` **before** opening versus just wrapping `open()` in `try`/`except`: why is the second one preferred, and what can change in the gap between the check and the open? Then explain the **atomic write** pattern (write to a temp file, then `os.replace()`) and what failure it protects a reader from.
10. *(Tie-back to Weeks 1, 2, 3, and 5.)* Trace one line of code all the way down: `text = open("data.txt").read()`. Name what happens at each layer — the path resolved against the working directory, the **system call** into the kernel and the **file descriptor** it returns (Week 5), the actual **disk read** and why it's the slow part (Week 1), the raw **bytes** that come back and the **decode** into text (Week 2), and the `str` **object** now sitting in RAM with a name bound to it (Week 3). Then name one realistic way each of those layers can fail.

### Practical Tasks

Each task is a separate, tiny Python file (think 5–20 lines). Run each one, look at the output, and write one sentence in your notes about what it showed you. Each task practices something from the questions above. **Task 6 is optional** — a stretch for when you want to go further.

1. **Task 1 — The same file, text and bytes.** *(Practices Q6.)* Write a short string containing a non-ASCII character (`"café\n"`) to a file in text mode with `encoding="utf-8"`. Then read that same file back twice — once in text mode (`"r"`) and once in binary (`"rb"`) — printing both results and the `len()` of each. Watch Week 2's str-vs-bytes distinction reappear, now coming through `open()`. **Concepts:** `open()` modes, `encoding=`, text vs binary, `len()` of `str` vs `bytes`.
2. **Task 2 — Paths without string glue.** *(Practices Q8.)* Using `pathlib.Path`, build a path with the `/` operator, then print its `.name`, `.suffix`, `.parent`, and `.resolve()`, and whether it `.exists()`. Then print `Path.cwd()` next to `Path(__file__).parent`. Now **run the script twice** — once from inside `week6/solutions/`, then again from the repo root (`python phase1/week6/solutions/task2_paths_with_pathlib.py`) — and watch `cwd()` change while the script's own directory stays put. That's the Q2 bug, reproduced on demand. **Concepts:** `pathlib.Path`, the `/` operator, `.name` / `.suffix` / `.parent` / `.resolve()`, `Path.cwd()`, `__file__`.
3. **Task 3 — Read a big file two ways and watch memory.** *(Practices Q7.)* Write a file with ~200,000 numbered lines. Then count its lines twice: once with `f.read().splitlines()` (whole file into RAM) and once with `for line in f:` (one line at a time). Wrap each with `tracemalloc.start()` / `tracemalloc.get_traced_memory()` and `time.perf_counter()`, and print the peak memory and time for both. Same answer, wildly different footprint — expect a difference of a few hundred times over. Two things to look for, because both are lessons rather than bugs: the streaming version may well be **slower in wall-clock time** even though it uses a fraction of the memory (that trade is exactly the point — it's what lets the same code survive a file bigger than your RAM), and the `.read()` version's peak memory comes out **several times larger than the file itself**, because `splitlines()` hands you 200,000 separate `str` objects, each carrying Week 3's object overhead. **Concepts:** writing in a loop, `f.read()` vs iterating a file object, `tracemalloc`, `time.perf_counter()`.
4. **Task 4 — Metadata is not contents.** *(Practices Q3.)* Take the file from Task 1 and print its `.stat()` fields: `st_size` in bytes, `st_mtime` formatted as a real date with `datetime.fromtimestamp()`, and the permission bits as `oct(st.st_mode)[-3:]`. Then append one line to the file and print the size and modification time again to watch both change. **Concepts:** `Path.stat()`, `st_size` / `st_mtime` / `st_mode`, `datetime.fromtimestamp()`, `oct()`, append mode `"a"`.
5. **Task 5 — Make the I/O errors happen on purpose.** *(Practices Q9.)* In three small `try`/`except` blocks, trigger and catch: opening a file that doesn't exist (`FileNotFoundError`), opening a *directory* as if it were a file (`IsADirectoryError` / `PermissionError`), and opening an existing file with mode `"x"` (`FileExistsError`). Print the message each one gives you. Then write one sentence on why catching the error beats checking `.exists()` first. **Concepts:** `FileNotFoundError`, `IsADirectoryError`, `FileExistsError`, `try` / `except`, mode `"x"`.
6. **Task 6 — Buffering, flushing, and an atomic write.** *(Optional — practices Q4 and Q9.)* Two parts. **(a)** Open a file for writing, write a line *without* closing it, and immediately try to read the file from a second handle — see nothing there yet; then call `.flush()` and read again to watch it appear. **(b)** Do a safe write: write the new contents to `config.tmp`, then `os.replace("config.tmp", "config.json")` to swap it into place in one atomic step, so a reader can never catch a half-written file. **Concepts:** `.flush()`, `os.fsync()`, `os.replace()`, atomic rename, buffering.
